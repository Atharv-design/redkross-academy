Lesson 5: Common Cryptographic Mistakes and How to Avoid Them
Part 1 — Hook

You have built the vault. The walls are three feet thick steel. The lock is a state-of-the-art biometric scanner. The alarm system is monitored 24/7 by a dedicated security team.

But you left the spare key under the doormat.

This is the story of almost every major cryptographic failure in history. The mathematics was sound. The algorithms were vetted by the world’s best cryptographers. The implementation passed every unit test. But a single, stupid mistake — a hardcoded key, a reused nonce, a forgotten padding check — blew the vault door off its hinges.

Cryptography is unique in engineering. In almost every other field, if you make a small mistake, the system degrades slightly. The bridge vibrates a little. The website loads a second slower. In cryptography, a single bit error — one wrong == instead of ===, one reused IV, one forgotten bounds check — destroys the entire security guarantee instantly. There is no “partial security.” The lock is either locked, or it is wide open.

This lesson is not about the math. It is about the discipline. It is a catalog of the specific, recurring, embarrassing mistakes that turn military-grade encryption into decorative text. If you master this list, you will avoid 95% of the cryptographic disasters that make headlines.

Part 4 — Concept from Scratch: The Fragility of Perfection

Here is the central sentence of this lesson.

In cryptography, the algorithm is rarely the problem; the implementation is almost always the problem.

Let me say that again, because it contradicts how most developers think about security.

In cryptography, the algorithm is rarely the problem; the implementation is almost always the problem.

AES-256-GCM has never been broken. ChaCha20-Poly1305 has never been broken. RSA-2048 has never been broken (classically). Ed25519 has never been broken. But systems using these exact algorithms are hacked every single day. Why? Because the developers treated cryptography like a LEGO set — snap the pieces together and it works. Cryptography is not LEGO. It is a minefield where the mines are invisible, and the map is written in a language you don’t speak.

Part 5 — The Hall of Shame: Top 10 Implementation Disasters
Mistake 1: Rolling Your Own Crypto (The Hubris Trap)

The Mistake: A developer thinks, “AES is too slow/big/complex. I’ll just XOR the data with a key stream I generate from a hash function. It’s basically a stream cipher, right?”

Why It Fails: Cryptographic design requires proving security against unknown future attacks. You cannot prove your homebrew cipher is secure; you can only fail to break it yourself. Real ciphers survive decades of public cryptanalysis. Yours survives until a intern with Python finds the pattern.

Real World: The Telegram MTProto v1 protocol used a homebrew construction (msg_key = SHA256(auth_key + msg) + AES-IGE). Researchers found it allowed chosen-ciphertext attacks and plaintext recovery. Zoomb initially used a custom AES-256 ECB mode for key distribution (fixed later).

The Rule: Never invent crypto. Never implement primitives. Use libsodium (crypto_box, crypto_secretbox), age, TLS 1.3, OpenSSL EVP API, Go crypto/tls, Rust ring``.

Mistake 2: ECB Mode — The “Penguin” Problem

The Mistake: Using AES in ECB (Electronic Codebook) Mode. Each block is encrypted independently: C_i = E(K, P_i).

Why It Fails: Identical plaintext blocks produce identical ciphertext blocks. Patterns in the plaintext (headers, images, repeated fields) are perfectly preserved in the ciphertext.

The Visual Proof: The “ECB Penguin.” Encrypt a bitmap image of Tux the penguin with AES-ECB. The ciphertext still looks like a penguin.

IMAGE 2 — ECB Mode Visual Failure: A side-by-side image comparison on a light background. Left: “Plaintext (Tux Penguin)” — clear penguin image. Right: “Ciphertext (AES-ECB)” — the penguin shape is clearly visible as noise patterns. Caption: “ECB Mode: Patterns Survive Encryption. Never Use ECB.” Light background, minimal text.

The Rule: Never use ECB. Use AES-GCM, ChaCha20-Poly1305, or AES-CBC + HMAC (with distinct keys).

Mistake 3: CBC Mode Without Authentication — The Padding Oracle

The Mistake: Using AES-CBC with a separate HMAC (or worse, no MAC at all). The developer thinks: “CBC provides confidentiality. I’ll add an HMAC later... or maybe not, it’s internal.”

Why It Fails: CBC mode is malleable. An attacker can flip bits in the ciphertext to flip predictable bits in the plaintext. Worse, if the server reveals whether padding is valid (via error message, timing, or exception), the attacker has a Padding Oracle. They decrypt the ciphertext byte-by-byte without the key.

Real World: POODLE (SSL 3.0), Lucky13 (TLS 1.0/1.1), Vaudenay’s Attack. Thousands of internal APIs still use unauthenticated CBC.

The Rule: Never use unauthenticated encryption. Use AEAD (AES-GCM, ChaCha20-Poly1305). If you must use CBC, use Encrypt-then-MAC (Encrypt, then HMAC the IV+Ciphertext with a separate key), and verify MAC before decryption (constant-time).

Mistake 4: Nonce/IV Reuse in GCM/ChaCha20 — The “Game Over” Button

The Mistake: Using AES-GCM or ChaCha20-Poly1305 with a static IV (all zeros), a counter that resets on restart, or a random IV that’s too short (64-bit) leading to collisions.

Why It Fails: AEAD modes (GCM, ChaCha20) are stream ciphers at heart. Ciphertext = Plaintext XOR Keystream(Key, Nonce). If you reuse (Key, Nonce), the Keystream is identical.

C1 = P1 XOR KS
C2 = P2 XOR KS
C1 XOR C2 = P1 XOR P2

The attacker XORs the two ciphertexts. The keystream cancels out. They get P1 XOR P2. With known plaintext (headers, JSON structure), they recover both plaintexts. They can also forge valid authentication tags for any message.

Real World: PlayStation 3 (ECDSA nonce reuse -> private key extracted). WPA2 KRACK (nonce reuse in handshake). Countless IoT devices using static nonces.

IMAGE 3 — The Nonce Reuse Catastrophe: A mathematical diagram on a light background. Top: “Correct Usage: Unique Nonce per Message” -> Nonce_1 -> Keystream_1 -> Ciphertext_1, Nonce_2 -> Keystream_2 -> Ciphertext_2. Bottom: “FATAL: Nonce Reused” -> Nonce_1 -> Keystream_1 -> Ciphertext_1, Nonce_1 -> Keystream_1 -> Ciphertext_2. Bottom box: C1 XOR C2 = P1 XOR P2. Red alert box: “KEYSTREAM REUSE = PLAINTEXT RECOVERY + FORGERY.” Light background, red/crimson alerts, clean math notation.

The Rule: Nonce reuse is fatal in AEAD. Use XChaCha20-Poly1305 (192-bit nonce, safe for random generation) or AES-GCM-SIV (nonce-misuse resistant). If using AES-GCM, use a 96-bit counter persisted to stable storage, or XChaCha20.

Mistake 5: Static IVs / Hardcoded IVs

The Mistake: byte[] iv = new byte[16]; (all zeros) or String IV = "1234567890123456"; in the code.

Why It Fails: This is just Nonce Reuse by another name. Every message encrypted with that key uses the same IV. In CBC, it leaks prefix equality. In GCM/ChaCha20, it’s catastrophic (see Mistake 4).

The Rule: IVs/Nonces must be unique per (Key, Message). Use a CSPRNG for 96-bit+ nonces (GCM) or 192-bit for XChaCha20. For CBC, use a random IV per message and prepend it to ciphertext.

Mistake 6: Using Encryption for Integrity (The “Encrypted = Tamper-Proof” Fallacy)

The Mistake: “I encrypted the cookie with AES, so the user can’t tamper with it.”

Why It Fails: Encryption provides Confidentiality, not Integrity.

CBC: Bit-flipping attacks modify plaintext predictably.
CTR/GCM/ChaCha20: XOR malleability. Flip bit in ciphertext -> flips bit in plaintext.
ECB: Block reordering, deletion, duplication.

Real World: ASP.NET ViewState (pre-4.5), Java ObjectInputStream deserialization, many JWT implementations using alg: none or symmetric keys without verification.

The Rule: Always use Authenticated Encryption (AEAD: AES-GCM, ChaCha20-Poly1305) or Encrypt-then-MAC. Never trust ciphertext integrity implicitly.

Mistake 7: Key/IV Derivation from Passwords Without KDF

The Mistake: key = password.getBytes("UTF-8"); or key = MD5(password); or key = SHA256(password);.

Why It Fails:

Low Entropy: Passwords have ~20-40 bits entropy. Keys need 128/256 bits.
No Salt: Same password = same key everywhere. Rainbow tables / precomputation.
Speed: MD5/SHA256 are fast. Attacker tries billions/sec on GPU.

The Rule: Always use a Password-Based Key Derivation Function (PBKDF).

Argon2id (Gold Standard): Memory-hard, GPU/ASIC resistant. m=64MB, t=3, p=4.
PBKDF2-HMAC-SHA256 (Legacy/Compliance): iterations >= 600,000 (OWASP 2023).
scrypt (Legacy): Memory-hard, but harder to tune than Argon2.
Never use fast hashes (MD5, SHA-1, SHA-256) directly.
Mistake 8: Insecure Random Number Generation

The Mistake: Math.random(), Random(), rand(), System.currentTimeMillis(), new Random(seed) for keys, nonces, salts, tokens, UUIDs.

Why It Fails: These are PRNGs (Pseudo-Random Number Generators), not CSPRNGs (Cryptographically Secure PRNGs). They are predictable. If attacker knows one output, they compute internal state and predict all future outputs (keys, nonces, session tokens, password resets).

Real World: Debian OpenSSL Bug (2008) - RNG seeded only with PID (32768 possibilities). Sony PS3 - ECDSA k reused (not random). Bitcoin Wallets - k generated by flawed Java SecureRandom on Android. Dual_EC_DRBG - NSA backdoored NIST standard.

The Rule: Always use OS CSPRNG.

Linux: /dev/urandom (or getrandom() syscall).
Windows: BCryptGenRandom, CryptGenRandom.
Java: SecureRandom (not Random).
Go: crypto/rand.Reader.
Python: secrets.token_bytes(), os.urandom().
Node: crypto.randomBytes().
Mistake 9: Timing Side-Channels in Verification

The Mistake: if (hmac(message, key) == received_mac) { ok } or if (password == stored_hash) { ok } or early-exit string comparison.

Why It Fails: == and memcmp exit early on first mismatch. Attacker measures response time to the nanosecond. valid_mac[0] == guess[0]? -> slightly faster. They brute-force the MAC byte-by-byte in 256 * 32 attempts instead of 2^256.

Real World: Xbox 360 (timing attack on HMAC), Google Keyczar (fixed), many custom JWT/HMAC verifications.

The Rule: Always use Constant-Time Comparison.

Go: hmac.Equal(mac1, mac2) / subtle.ConstantTimeCompare
Java: MessageDigest.isEqual()
Python: hmac.compare_digest()
Node: crypto.timingSafeEqual()
Go/Rust/JS: Use subtle.ConstantTimeCompare or equivalent.
Mistake 10: Hardcoded Secrets / Keys in Code / Config / Containers

The Mistake: const string API_KEY = "sk_live_..."; private static final String AES_KEY = "..."; docker build --build-arg SECRET=... .env committed to git.

Why It Fails:

Git History: git log -p reveals all past secrets. git push to public repo = instant compromise.
Docker Layers: docker history / docker save extracts build args/env vars.
CI Logs: Build pipelines print env vars.
Insider Threat: Every dev/contractor sees production keys.

Real World: Uber (2016) - AWS keys in GitHub repo -> 57M users breached. Samsung - source code with signing keys leaked. NPM packages - malicious packages stealing .env files.

The Rule: Never put secrets in code, config files, Dockerfiles, or build args.

Runtime Injection: Environment variables injected at runtime (K8s Secrets, AWS Secrets Manager, Vault, Doppler, 1Password CLI).
Build Time: Only public config.
Rotation: Automate rotation (AWS Secrets Manager rotation, Vault dynamic secrets).

Part 7 — Crypto Agility: Future-Proofing Your Implementation

Crypto Agility is the ability to swap cryptographic algorithms, key sizes, or protocols without rewriting your application logic.

Why You Need It:

Quantum Computing: RSA/ECC will break. You need to swap to Kyber/Dilithium.
New Attacks: SHA-1 broken -> SHA-256. SHA-256 broken? -> SHA-3.
Policy Changes: FIPS 140-3 mandates new modes. GDPR requires key rotation.
Protocol Updates: TLS 1.2 -> 1.3 -> 1.4(?)
Designing for Agility
Abstract the Primitive: Never call AES_encrypt() directly. Call crypto.encrypt(plaintext, policy="current").
Parameterize Everything: Key sizes, algorithms, modes, KDF parameters in config, not code.
Version Your Crypto: Every ciphertext/certificate/signature carries a Version/Algorithm ID.
v1::aes256gcm::nonce::ciphertext::tag
v2::xchacha20poly1305::nonce::ciphertext::tag
Parser reads version, dispatches to correct implementation.
Negotiation: TLS does this (ciphersuite negotiation). Your protocols should too.
Deprecation Pipeline: Supported -> Deprecated (Accept Only) -> Forbidden (Reject). Automate scanning for deprecated versions.
Part 7 — Guided Mini-Lab: The Cryptographic Code Audit

In this lab, you are a security auditor reviewing a pull request for a new “Secure File Storage” feature. The developer has written the encryption module. Find the vulnerabilities.

The Code (Pseudocode/Python-style)
python
# secure_storage.py - PR #402
import os
from Crypto.Cipher import AES
from Crypto.Hash import SHA256
from Crypto.Random import get_random_bytes

# Global constants
MASTER_KEY = b"SuperSecretMasterKey123456"  # 32 bytes
IV = b"0000000000000000"  # 16 bytes

def derive_key(password: str) -> bytes:
    # "Custom KDF for speed"
    return SHA256.new(password.encode()).digest()

def encrypt_file(plaintext: bytes, password: str) -> bytes:
    key = derive_key(password)
    cipher = AES.new(key, AES.MODE_CBC, IV)
    # PKCS7 Padding
    pad_len = 16 - (len(plaintext) % 16)
    padded = plaintext + bytes([pad_len] * pad_len)
    ciphertext = cipher.encrypt(padded)
    return IV + ciphertext  # Prepend IV for storage

def decrypt_file(ciphertext: bytes, password: str) -> bytes:
    key = derive_key(password)
    iv = ciphertext[:16]
    ct = ciphertext[16:]
    cipher = AES.new(key, AES.MODE_CBC, iv)
    padded = cipher.decrypt(ct)
    # Remove padding
    pad_len = padded[-1]
    return padded[:-pad_len]

def generate_api_token() -> str:
    # "Fast token generation"
    import random
    return "token_" + str(random.randint(100000, 999999))

def verify_hmac(message: bytes, received_mac: bytes, key: bytes) -> bool:
    expected = hmac.new(key, message, SHA256).digest()
    return expected == received_mac  # Standard comparison

Part 8 — Summary and Glossary

Here is what we covered.

Cryptographic security lives or dies in the implementation, not the algorithm. The Top 10 Mistakes are: Rolling Your Own Crypto, ECB Mode, Unauthenticated CBC (Padding Oracles), Nonce/IV Reuse in AEAD, Static/Hardcoded IVs, Encryption Without Integrity, Weak Key Derivation, Insecure RNG, Timing Side-Channels, and Hardcoded Secrets.

The defense is discipline: Use high-level libraries (libsodium, age, TLS 1.3), enforce the Crypto Code Review Checklist, and build Crypto Agility into your architecture so you can swap primitives when (not if) they break.

Glossary of Key Terms:

Rolling Your Own Crypto: Implementing custom cryptographic primitives or protocols instead of using vetted libraries.
ECB Mode (Electronic Codebook): Block cipher mode encrypting blocks independently; leaks patterns.
Padding Oracle Attack: Attack on unauthenticated CBC mode exploiting padding validation errors.
AEAD (Authenticated Encryption with Associated Data): Encryption providing confidentiality + integrity simultaneously (GCM, ChaCha20-Poly1305).
Nonce/IV Reuse: Using the same (Key, Nonce) pair twice; catastrophic in stream ciphers/AEAD.
Padding Oracle: An attack exploiting padding validation error messages to decrypt ciphertext.
KDF (Key Derivation Function): Algorithm deriving cryptographic keys from passwords/secrets (Argon2id, PBKDF2).
CSPRNG (Cryptographically Secure PRNG): Random number generator safe for key/nonce generation.
Constant-Time Comparison: Comparison algorithm taking same time regardless of input similarity.
Encrypt-then-MAC: Composing encryption and authentication correctly (Encrypt, then MAC the ciphertext).
Crypto Agility: Designing systems to easily swap algorithms/parameters without code rewrite.
Padding Oracle: An attack exploiting padding validation error messages to decrypt ciphertext.
Timing Side-Channel: Attack measuring execution time to extract secrets (keys, MACs, passwords).
ECB Mode: Block cipher mode encrypting blocks independently; leaks patterns.
AEAD: Authenticated Encryption with Associated Data (GCM, ChaCha20-Poly1305).
Nonce/IV Reuse: Using the same (Key, Nonce) pair twice; catastrophic in stream ciphers/AEAD.
KDF: Key Derivation Function (Argon2id, PBKDF2, scrypt).
CSPRNG: Cryptographically Secure Pseudo-Random Number Generator.
