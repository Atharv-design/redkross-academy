Lesson 4: Data at Rest vs. Data in Transit
Part 1 — Hook

Imagine you are a spy carrying a briefcase. Inside the briefcase is a notebook containing the names of every undercover agent in your country.

Scenario A: You are sitting in a safe house. The briefcase is locked in a steel safe, bolted to the floor, inside a locked room, inside a guarded building. The notebook is at rest. The threat is someone breaking into the safe house, finding the safe, cracking it, and reading the notebook.

Scenario B: You are on a train. You must hand the briefcase to another agent at the next station. The briefcase is in transit. The threat is someone stealing the briefcase from your hand, swapping it with an identical fake, or opening it while you sleep.

The notebook is the same. The names are the same. But the threats are completely different. The defenses you use in the safe house (thick walls, guards, heavy locks) are useless on the train. The defenses you use on the train (handcuffs, disguises, constant vigilance) are useless in the safe house.

This is the exact difference between Data at Rest and Data in Transit. The data is the same notebook. But the environment changes, the threats change, and therefore the cryptographic defenses must change.

Most security failures happen because engineers use the “safe house” defenses for the “train” scenario, or vice versa. They encrypt a database (at rest) but send the backup over an unencrypted FTP connection (in transit). They use TLS for the web connection (in transit) but store the passwords in plain text in the database (at rest).

This lesson teaches you how to distinguish these two states, understand their unique threat models, and apply the correct cryptographic controls for each.

Part 2 — Learning Objectives

By the end of this lesson you will be able to:

Part 4 — Concept from Scratch: The Two States of Data

Here is the central sentence of this lesson.

Data does not stay still. It exists in two distinct states — at rest and in transit — and each state faces a completely different enemy, requiring a completely different shield.

Let me say that again, because it is the most important sentence in this lesson.

Data does not stay still. It exists in two distinct states — at rest and in transit — and each state faces a completely different enemy, requiring a completely different shield.

Data is like water. It can be ice (solid, at rest, stored in a container) or a river (liquid, in transit, flowing through pipes). Ice needs a freezer (storage encryption). A river needs pipes that don’t leak (transport encryption). If you try to freeze the river to protect it, you stop the flow. If you try to pipe the ice, it shatters the pipes.

Part 5 — How It Works: Data at Rest — The Fortress

Data at Rest is data stored on a persistent medium: hard drives, SSDs, databases, file servers, backups, archives, mobile devices, USB drives. It is not moving. It is waiting.

The Threat Model for Data at Rest

The enemy here is Access. The attacker has time. They can steal the physical drive. They can image the disk. They can boot a live Linux USB on a stolen laptop. They can access backup tapes in an offsite vault. They can be a malicious insider with admin rights.

The goal of encryption at rest is Confidentiality despite Access. Even if the attacker holds the hard drive in their hand, they cannot read the data.

The Mechanism: Full Disk Encryption (FDE)

Full Disk Encryption (FDE) encrypts the entire storage volume, including the operating system, swap files, and temporary files.

How it works: When the system boots, the user enters a passphrase (or inserts a hardware token). This unlocks the Master Key (KEK - Key Encryption Key). The KEK decrypts the Data Encryption Key (DEK). The DEK is used by the CPU’s AES-NI instructions to encrypt/decrypt blocks on the fly as they are read/written.
Hardware Acceleration: Modern CPUs (Intel AES-NI, ARM Crypto Extensions) perform AES encryption/decryption at line speed with near-zero performance penalty.
Examples: BitLocker (Windows), FileVault (macOS), LUKS/dm-crypt (Linux), OPAL SEDs (Self-Encrypting Drives).

File and Database Encryption (Granular Encryption)

FDE protects the whole disk. But what if the OS is running and an attacker dumps the RAM? Or an SQL injection dumps the database? FDE is “open” while the system runs.

File/Database Encryption encrypts specific data before it hits the disk.

Application-Layer Encryption: The application encrypts sensitive fields (SSN, Credit Card, PII) using a DEK before INSERTing into the DB. The DB only sees ciphertext.
Transparent Data Encryption (TDE): The database engine encrypts the data files automatically. The DEK is protected by a certificate/key in the DB master key hierarchy.
Format-Preserving Encryption (FPE): Encrypts data while preserving format (e.g., a 16-digit credit card stays a 16-digit number). Essential for legacy systems that validate format.
The Key Management Hierarchy (The Crown Jewels)

Encryption at rest is only as strong as the Key Management. If the keys are stolen, the encryption is useless.

KEY MANAGEMENT HIERARCHY
┌─────────────────────────────────────┐
│  Root of Trust (Hardware/HSM)       │  ← Generates/Stores Master Keys
├─────────────────────────────────────┤
│  Key Encryption Keys (KEKs)         │  ← Encrypts DEKs
├─────────────────────────────────────┤
│  Data Encryption Keys (DEKs)        │  ← Encrypts Actual Data
├─────────────────────────────────────┤
│  Data (Ciphertext)                  │
└─────────────────────────────────────┘
Root of Trust: Hardware Security Module (HSM), TPM, Cloud KMS (AWS KMS, Azure Key Vault, GCP KMS), HashiCorp Vault.
Key Rotation: DEKs must be rotated periodically. The KEK wraps the new DEK. Old DEKs are retained to decrypt old data.
Key Destruction: Crypto-shredding. Deleting the DEK renders the data permanently unreadable. This is how you “delete” encrypted data instantly.
The Threat: Cold Boot Attacks & RAM Dumping

When the system is on, the DEK sits in RAM. An attacker with physical access can freeze the RAM (cold boot attack) or DMA attack via Thunderbolt/PCIe to dump the keys.

Mitigations:

TME (Total Memory Encryption): Intel TME / AMD SME encrypts RAM itself.
Pre-boot Authentication: FDE requires password before OS loads (prevents DMA attacks on locked screen).
Memory Scrubbing: Wipe keys from RAM on lock/sleep/hibernate.
Part 6 — How It Works: Data in Transit — The Armored Convoy

Data in Transit is data moving across a network: HTTP/HTTPS traffic, API calls, database replication, email (SMTP), file transfers (SFTP/rsync), VPN traffic, IoT telemetry, DNS queries.

The Threat Model for Data in Transit

The enemy here is Interception and Manipulation. The attacker controls the network (the pipe). They can:

Eavesdrop (Passive): Sniff packets (Wi-Fi sniffing, BGP hijacking, ISP tapping).
Tamper (Active - MITM): Modify packets (inject scripts, change bank account numbers, strip TLS).
Replay: Capture a valid request (e.g., “transfer $100”) and replay it 100 times.
Impersonation (Spoofing): Fake the server (phishing site) or fake the client (stolen session cookie).

The goal of encryption in transit is Confidentiality, Integrity, and Authentication of the Channel.

The Mechanism: TLS (Transport Layer Security)

TLS is the backbone of data-in-transit security. It provides:

Authentication: Server proves identity via Certificate (X.509).
Key Exchange: Establishes a shared session key (ECDHE).
Encryption: Symmetric encryption of payload (AES-GCM / ChaCha20-Poly1305).
Integrity: AEAD (Authenticated Encryption) tags on every record.

TLS 1.3 (The Modern Standard):

Removed: RSA key exchange, Static DH, CBC mode, RC4, SHA-1, Compression, Renegotiation.
Mandatory: (EC)DHE for Perfect Forward Secrecy, AEAD Ciphers (AES-GCM, ChaCha20-Poly1305).
0-RTT: Optional early data for performance (with replay risks).

Beyond HTTPS: VPNs, mTLS, and WireGuard
VPNs (IPsec / WireGuard): Create an encrypted tunnel for all traffic from a device/network. WireGuard uses modern crypto (Curve25519, ChaCha20-Poly1305, BLAKE2s) in ~4000 lines of code. Simpler, faster, auditable than IPsec.
mTLS (Mutual TLS): Both client and server present certificates. Used for Service Mesh (Istio, Linkerd), Zero Trust networks. Authenticates both sides.
QUIC / HTTP/3: UDP-based transport with TLS 1.3 built-in. Reduces head-of-line blocking. Default encryption.
Certificate Pinning & DANE

Certificate Pinning: The client (app/browser) hardcodes the expected certificate hash or public key. Prevents rogue CAs from issuing valid certs for your domain.

Risk: Cert rotation breaks the app. Use Backup Pins or HPKP (deprecated) / Expect-CT headers.

DANE (DNS-based Authentication of Named Entities): Stores TLSA records in DNSSEC-signed DNS. The DNS becomes the trust anchor, not the CA.

Part 7 — The Gray Zone: Where Rest Meets Transit

The most dangerous moment is the transition.

Scenario 1: Database Backup (Rest → Transit → Rest)
DB dumps to disk (Rest).
Backup agent reads file, sends to Cloud Storage via HTTPS (Transit).
Cloud provider stores object (Rest).
Failure Point: If the backup agent uses HTTP, or the cloud bucket has no SSE (Server-Side Encryption), the data is exposed in the gray zone.
Scenario 2: Application Boot (Transit → Rest → Memory)
App downloads config/secrets from Vault via mTLS (Transit).
App writes config to local disk for caching (Rest - unencrypted!).
App loads config into RAM (Memory).
Failure Point: The temporary config file on disk is unencrypted. An attacker with disk access steals the secrets.
Scenario 3: Email Attachment (Rest → Transit → Rest)
User attaches encrypted PDF (Rest).
Sends via SMTP with STARTTLS (Transit - Opportunistic! May downgrade).
Recipient downloads to disk (Rest).
Failure Point: STARTTLS is opportunistic. Attacker strips TLS (STRIPTLS attack). Email travels in cleartext.
The “Data in Use” (Memory) Problem

Data is decrypted in RAM (Memory) for the CPU to process. This is the “Third State.”

Threats: RAM scraping (POS malware), SGX/Enclave side-channels, hypervisor access (cloud), swap file leakage.
Defenses: Intel SGX / AMD SEV / ARM CCA (Confidential Computing), TME (Total Memory Encryption), careful memory handling (mlock, zeroing).
Part 7 — Common Implementation Anti-Patterns & Pitfalls
Anti-Pattern 1: Encrypting at Rest but Not in Transit (or Vice Versa)
The Mistake: “We encrypt our database (AES-256), so we’re secure.” But the app talks to the DB over plaintext TCP on port 3306.
Why it Fails: Anyone on the VLAN sniffs the SQL queries and results. Encryption at rest protects the files, not the protocol.
Fix: Enforce TLS for all internal traffic (mTLS for DB connections).
Anti-Pattern 2: TLS Termination at the Load Balancer (The “Unencrypted Backend”)
The Mistake: TLS terminates at the AWS ALB / Nginx / HAProxy. Traffic from LB to backend servers is plain HTTP.
Why it Fails: Anyone with access to the internal network (compromised container, rogue employee, misconfigured SG) sees all traffic in cleartext. PII, tokens, passwords exposed.
Fix: End-to-End TLS (mTLS) from Client → LB → Backend. Or use a Service Mesh (Istio/Linkerd) for automatic mTLS.
Anti-Pattern 3: Storing Keys Next to the Lock (Co-location)
The Mistake: The database encryption key is stored in a config file on the same server as the database. Or the S3 bucket encryption key is in the same AWS account/region.
Why it Fails: If the server is compromised (RCE, SSRF), the attacker reads the config file, gets the key, decrypts the DB. The encryption provided zero value.
Fix: External KMS/HSM. The application requests decryption from KMS; the key never touches the application disk/memory in plaintext (envelope encryption).
Anti-Pattern 4: Ignoring Metadata / Traffic Analysis
The Mistake: “We use TLS 1.3, so the attacker sees nothing.”
Why it Fails: The attacker sees metadata: Packet sizes, timing, frequency, destination IPs, SNI (Server Name Indication). They know who you talk to, when, and how much.
Fix: Traffic shaping, padding, fixed-size records, mixnets (for high-value), DNS over HTTPS (DoH) / DNS over TLS (DoT) to hide SNI/DNS.
Anti-Pattern 5: Forgetting the Backup / Archive Path
The Mistake: Production DB is encrypted (TDE). Backups are written to NFS share / Tape / S3 without encryption, or with a different, weaker key.
Why it Fails: Attackers target backups (often less monitored, retained longer, stored offsite). The 2017 Equifax breach involved unencrypted backup files.
Fix: Enforce encryption at the source for all derived copies. Use the same KMS/DEK hierarchy for backups.
Part 8 — Attacker vs Defender Viewpoint
The Attacker’s Playbook
ATTACKER PLAYBOOK: REST vs TRANSIT
┌─────────────────────────────────────────────────────────────────┐
│ TARGETING DATA AT REST                                          │
│  1. Steal Backup Tapes / Cloud Snapshots (Low Risk, High Value) │
│  2. Compromise Backup Server → Exfiltrate Dump Files            │
│  3. Cold Boot Attack / DMA Attack on Locked Laptops             │
│  4. Insider: Copy DB Files to USB / Personal Cloud              │
│  5. Exploit Backup Misconfiguration (Public S3 Bucket)          │
├─────────────────────────────────────────────────────────────────┤
│ TARGETING DATA IN TRANSIT                                       │
│  1. ARP Spoofing / Rogue AP → MITM on LAN/Wi-Fi                 │
│  2. BGP Hijacking → Reroute Traffic to Attacker's Server        │
│  3. SSL Stripping / STARTTLS Downgrade → Cleartext Capture      │
│  4. Compromised CA / Rogue Certificate → Valid MITM Cert        │
│  4. Replay Attacks on Non-Idempotent APIs                       │
└─────────────────────────────────────────────────────────────────┘
The Defender’s Hardening Playbook
Default Deny, Encrypt Everything: No “sensitive data” classification needed. Encrypt all disks, all databases, all backups, all network links.
Centralized Key Management (KMS/HSM): Keys never on disk. Envelope encryption everywhere.
Zero Trust Network: No “trusted internal network.” mTLS everywhere. Service Mesh for automatic mTLS.
Automated Certificate Management: ACME (Let’s Encrypt / Internal CA) for short-lived certs (24h-90d). Automated rotation.
Monitor the Gray Zones: Alert on unencrypted protocols (FTP, Telnet, HTTP, plain DB ports). Scan for unencrypted data at rest (DLP tools).
Test the Gray Zones: Penetration test the backup/restore pipeline. Intercept internal traffic. Verify encryption end-to-end.

Part 10 — Summary and Glossary

Here is what we covered.

Data at Rest is stored data. Its enemy is Physical/Logical Access. We defend it with Full Disk Encryption (FDE), File/Database Encryption (TDE/Application-layer), and rigorous Key Management (KMS/HSM, Envelope Encryption, Rotation, Crypto-shredding).

Data in Transit is moving data. Its enemy is Network Interception/Tampering. We defend it with TLS 1.3 (AEAD, PFS), mTLS / Service Mesh, WireGuard / IPsec VPNs, and Certificate Pinning / DANE.

The Gray Zone is where data transitions states (Backups, ETL, Caching, Email). Most breaches occur here. We must enforce encryption continuously across state boundaries.

Key Management is the Root of Trust. Use HSMs/Cloud KMS. Envelope Encryption. Never store keys next to data. Automate rotation and destruction.

Part 11 — Summary and Glossary

Glossary of Key Terms:

Data at Rest: Data stored on persistent media (disk, DB, backup, tape).
Data in Transit: Data moving across a network (HTTP, DB replication, email, API).
Full Disk Encryption (FDE): Encrypts entire storage volume (BitLocker, LUKS, FileVault).
Transparent Data Encryption (TDE): Database engine encrypts data files automatically.
Application-Layer Encryption: Application encrypts specific fields before storage.
Envelope Encryption: Encrypt data with DEK, encrypt DEK with KEK (from KMS/HSM).
Key Encryption Key (KEK): Key used to encrypt other keys (Data Encryption Keys).
Data Encryption Key (DEK): Key used to encrypt the actual data payload.
Hardware Security Module (HSM): Physical device for secure key storage and crypto operations.
Total Memory Encryption (TME): CPU feature encrypting RAM (Intel TME, AMD SME).
TLS 1.3: Modern transport protocol with mandatory PFS and AEAD ciphers.
mTLS (Mutual TLS): Both client and server authenticate via certificates.
Service Mesh: Infrastructure layer handling mTLS, observability, traffic control (Istio, Linkerd).
Certificate Pinning: Hardcoding expected certificate hash in client to prevent rogue CA attacks.
Data in Use: Data being processed in CPU/RAM (protected by Confidential Computing/Enclaves).
Crypto-shredding: Rendering encrypted data unreadable by destroying the encryption key.
SNI (Server Name Indication): TLS extension revealing hostname (visible even in TLS 1.3 ClientHello).
Perfect Forward Secrecy (PFS): Session keys not compromised by long-term key compromise (ECDHE).
Side-Channel Attack: Exploiting physical implementation (timing, power, EM) to extract keys.
