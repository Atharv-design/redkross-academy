Course 01: Introduction to Cybersecurity
Module 2: Core Principles
Lesson 6: Secure Defaults
Part 1 — Hook

You buy a new laptop. It comes out of the box. You turn it on for the first time. What state is it in?

If you are lucky, it has a password requirement, a lock screen, an automatic update setting, and a firewall that is turned on. If you are unlucky — and most of us are — it has a blank password, updates that only install when you remember to click “yes,” and a firewall that is off by default, waiting for you to find the setting and turn it on.

That laptop is not secure. It is a security risk wearing a thin casing. And it is not alone. Most software ships this way, because shipping with the safest settings would annoy some customers, and the sales team fears that annoyance more than the security team fears the breach.

Secure defaults is the principle that the safe choice should be the default choice. The user should not have to be a security expert to be safe. The product should protect them out of the box, before they have read a single page of documentation, before they have clicked a single setting.

This lesson is about flipping the burden of security away from the user and onto the product. It is the most practical lesson in Module 2, because it is the one that determines whether the other principles actually reach real people.

Part 2 — Learning Objectives

By the end of this lesson you will be able to:

Explain why products ship with insecure defaults.
Identify secure versus insecure defaults in common software.
Apply the principle to your own devices and accounts.
Explain how secure defaults relate to the other principles in Module 2.
Part 3 — Prerequisites

You have finished Module 1 and Module 2 Lessons 1 to 5. You know the CIA triad, AAA, least privilege, defence in depth, and zero trust. Secure defaults is what you get when you apply all of them before the user ever opens the product.

Part 4 — Concept from Scratch

Here is the central sentence of this lesson.

A secure default is a setting that protects the user without requiring them to know anything about security, and the goal of every product is to make the secure choice the choice that happens automatically.

Let me say that again, because it is the difference between a product that is safe and a product that is safe only if the user reads the manual.

A secure default is a setting that protects the user without requiring them to know anything about security, and the goal of every product is to make the secure choice the choice that happens automatically.

The principle has three parts, and each one is a test you can apply to any product you use.

Part 1: Safe out of the box. When the product is first installed or first turned on, it should be in its safest configuration. Nothing should be open, nothing should be shared, nothing should be accessible by default. The user should have to take a deliberate action to make the product less safe.

Part 2: No expertise required. The safe configuration should not require the user to understand firewalls, encryption, permissions, or authentication. A grandmother should be able to be safe without reading a single warning message. If safety requires expertise, then only experts will be safe, and everyone else will be a vulnerability.

Part 3: Easy to stay safe, hard to be unsafe. The secure path should be the path of least resistance. The insecure path should require extra steps, extra clicks, and extra warnings. If being safe is harder than being unsafe, users will choose unsafe, because they are busy and they are tired and they are not thinking about security.

Part 5 — How It Works: The Principle, the Exceptions, and the Examples
What a Secure Default Looks Like

Let us make this concrete. Here are the secure defaults for a modern device or application, and the insecure alternative in each case.

Area	Secure default	Insecure default
Password	Requires a strong password or passphrase. Blocks login after a few failed attempts.	Blank password. No strength requirement. Unlimited attempts.
Updates	Installs security updates automatically.	Asks the user to click “remind me later.”
Encryption	Encrypts the disk and all data by default.	Data is stored in plain text.
Sharing	Nothing is shared by default. The user must explicitly choose to share.	Everything is shared with everyone on the network.
Permissions	Apps get no permissions by default. The user grants them one at a time, when needed.	Apps get all permissions on install.
Network	Rejects unencrypted connections. Blocks known malicious domains.	Accepts everything, including fake websites that look real.
Privacy	Tracks nothing by default. Location, contacts, and camera access are off.	Tracks everything. Location is on. Camera and microphone are on.
Backup	Backs up automatically to a secure location.	No backup exists until the user sets one up.
Session	Logs out automatically after inactivity.	Stays logged in forever.
Remote access	Disabled by default.	Enabled by default, with a weak password.

Every single one of these is a choice that a product developer made. And in almost every case, the insecure choice was made because it was easier for the user in the short term, and the security team was overruled.

Why Products Ship Insecure

This is the uncomfortable part, and it is important to understand it, because it explains why secure defaults are the exception rather than the rule.

Users complain about security. A strong password requirement is annoying. A mandatory update restart is inconvenient. A permission prompt that appears every time is irritating. Customer support is flooded with complaints, and the product team — who are measured on user satisfaction, not on security — relaxes the settings.

The harm is invisible. A security breach is rare for any single user, and it happens to someone else. Annoyance is immediate, and it happens to the user in front of the product. The product team feels the annoyance and does not feel the breach. The asymmetry is overwhelming, and it pushes every product toward insecure defaults.

The competitor does not care. If Company A ships with strong security and Company B ships with weak security, Company B’s users have an easier first experience. Company A looks slow and strict. In a market where the first impression is everything, security is a competitive disadvantage — until the breach hits, and then it is a competitive advantage too late.

No one is in charge. Security is everyone’s responsibility and therefore no one’s responsibility. The engineer wants the feature. The designer wants the flow. The product manager wants the metric. The security team is the one saying no, and security teams are regularly understaffed and overruled.

The result: secure defaults are an active choice that has to be fought for. They are not the natural state of software. They are a victory that has to be won, again and again, by people who understand that the invisible harm of a breach is worse than the visible annoyance of a password prompt.

The Two Legitimate Exceptions

As with least privilege, there are situations where the secure default is not the right answer.

Usability-critical systems. In an emergency — a hospital during a crisis, a flight control system, a power grid — the priority is availability and speed. Security controls that slow down the response can themselves become a safety risk. In these systems, the default may be less restrictive, because the cost of a delay is higher than the cost of a breach. This is the exception, not the rule, and it must be documented and reviewed.

Legacy compatibility. Some software must work with old systems that do not support modern security. A factory’s control system running on a 1990s operating system cannot use modern encryption. In these cases, the secure default is impossible, and the organisation must compensate with other controls — isolation, monitoring, and physical security. The default is insecure, but the risk is understood and managed.

The rule for both: the exception must be documented, reviewed, and compensated. If the insecure default exists because “users complained,” that is not an exception. That is a failure.

Part 6 — Attack and Defence View

Let us now look at secure defaults from the attacker’s perspective, because that is how you learn what they are for.

How the attacker exploits insecure defaults. The attacker does not target the expert. They target the default. An attacker’s automated tools scan millions of devices for the same hundred insecure defaults: a router with the default password “admin,” a camera with the default credentials printed on the label, a database that is accessible without authentication, a service that exposes its version number and tells the attacker exactly which exploit to use.

The Mirai botnet from Module 1 worked this way. It scanned the internet for cameras and routers with default passwords, logged in, and added them to the botnet. The victims were not chosen. They were simply the devices that shipped with the worst defaults and were never changed. The attack was automated, and it worked at enormous scale, because insecure defaults are common.

The defender’s strategy is to make the default safe, so that the automated attack simply skips the device. A camera that requires a unique password out of the box is not interesting to the botnet scanner. It is invisible. The secure default is the defence that costs nothing at scale, because it protects every user without requiring any of them to do anything.

The most important sentence in this lesson: Secure defaults are the only security control that works on users who do not know they need protection.

Part 7 — Common Mistakes Beginners Make

Mistake 1: Thinking secure defaults are about the user being careful. They are not. They are about the product being safe before the user has a chance to be careful. A user who forgets to set a password is not careless. They are normal. The product should have protected them anyway.

Mistake 2: Confusing security with complexity. Beginners assume that a secure product must be complicated, full of warnings and prompts. It is the opposite. The best security is invisible. The best secure default is the one the user never notices, because everything just works and it is safe. Complexity is a failure of design, not a sign of security.

Mistake 3: Assuming that users will read the documentation. They will not. Most users never open the manual. Most never read a privacy policy. Most never change a single default setting. Any security model that depends on the user reading something is protecting a small fraction of users and leaving everyone else exposed.

Mistake 4: Ignoring the update problem. The most common insecure default in the world is “do not install updates automatically.” Users postpone updates indefinitely, and the security team knows that the patch that would have prevented the breach is sitting in the user’s download folder, unopened. Automatic updates are the single most effective security control available, and they are a secure default.

Mistake 5: Applying secure defaults only to your own devices. The principle applies to everything you use. Your email provider, your social network, your cloud storage, your bank — all of them should have secure defaults. If they do not, you are exposed through no fault of your own. Learn to look at a service and ask: what is this safe by default, and what did the company choose to make insecure?

Part 8 — Guided Mini-Lab: Check Your Defaults

Let us now check the defaults on your own devices and accounts. This takes 20 minutes. Go through the list and check each item.

Your phone:

Is the lock screen on? Does it require a password, PIN, or biometric? If it is set to “swipe only” or “none,” change it now.
Are updates installed automatically? Check the update settings.
Is the disk encrypted? On Android, this is in Security. On iOS, it is automatic when you set a passcode.
Do apps ask for permissions one at a time, or did they get them all on install? Review each app’s permissions and remove the ones it does not need.

Your computer:

Does it require a password to wake from sleep or unlock? Enable it if it is off.
Are security updates installed automatically? Turn this on.
Is the firewall on? Check. If it is off, turn it on.
Do you have a backup that runs automatically? Set one up if you do not have one.

Your important accounts:

Does your email require a password? Is MFA enabled? If MFA is not on, turn it on now. This is the single most important thing you will do today.
Does your bank require a strong password and alert you to new logins? Check.
Do the apps connected to your accounts have only the permissions they need? Review and remove the ones you do not use.

Part 9 — Why This Matters for the Rest of Module 2

Let me say something plainly.

Secure defaults is the principle that makes the other principles reach real people. Least privilege, defence in depth, and zero trust are all excellent architectures, but they only protect the people who configure them correctly. Secure defaults is the principle that says: the protection should be built in, so that it does not depend on the user being competent.

The rest of Module 2 is about what you build. Secure defaults is about making sure it is built before the user ever opens the box.

The case studies in Lesson 8 will show you what happens when defaults are insecure. Every major breach we have studied — every single one — involved a default that was left open, a setting that was never changed, or an update that was never installed. The attackers did not break in. They walked through doors that were open by default.

Part 10 — Summary and Glossary

Here is what we covered.

A secure default is a setting that protects the user without requiring security expertise. It has three parts: safe out of the box, no expertise required, and easy to stay safe while hard to be unsafe.

Products ship with insecure defaults because users complain about security, the harm of a breach is invisible and distant, competitors do not penalise insecurity, and no single person is responsible for fixing it. Secure defaults are an active choice that has to be fought for.

The secure defaults for a modern device include strong passwords, automatic updates, encryption, no sharing by default, no permissions by default, encrypted connections, no tracking, automatic backups, automatic logout, and disabled remote access.

The exceptions are usability-critical systems and legacy compatibility, both of which must be documented, reviewed, and compensated.

Secure defaults are the only security control that works on users who do not know they need protection. The Mirai botnet succeeded because too many devices shipped with default passwords.

Glossary of 8 terms:

Secure default — a setting that protects the user without requiring security expertise.
Default — the state of a product when it is first installed or turned on.
Automatic update — a security update that installs itself without requiring the user to click anything.
Fail closed — the secure choice when a system cannot decide: deny access rather than allow it.
Fail open — the insecure choice when a system cannot decide: allow access to avoid breaking functionality.
Permission — the ability of an app to access a resource on a device.
Disk encryption — encrypting all the data on a hard drive so that it cannot be read if the device is stolen.
Insecure by default — a product that ships with unsafe settings and requires the user to fix them.
