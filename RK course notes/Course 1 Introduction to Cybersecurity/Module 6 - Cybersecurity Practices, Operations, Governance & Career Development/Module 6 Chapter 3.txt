Lesson 3: Security Operations and Incident Management
Understanding the Heartbeat of Security Operations

Security operations is the nervous system of an organization’s defense. It is not a single tool or a team sitting in a dark room staring at blinking lights. It is a continuous, disciplined cycle of collecting data, making sense of noise, deciding what matters, acting decisively, and learning from every event. Most organizations fail not because they lack tools, but because they treat operations as a checklist rather than a living process. They buy a SIEM but never tune the rules. They hire analysts but give them no playbooks. They write an incident response plan once, print it, bind it, and leave it on a shelf until the day ransomware encrypts the file server — at which point nobody remembers where the printed copy is.

Security operations is the discipline of turning raw noise into actionable intelligence. It is the bridge between the theoretical controls you design and the messy reality of an active intrusion. It demands rigor in logging, intelligence in correlation, speed in response, and honesty in post-mortem. This lesson walks through the pillars that make security operations effective: logging and monitoring that actually see what matters, SIEM fundamentals that turn noise into signal, an incident response lifecycle that survives contact with the enemy, vulnerability management that actually reduces risk, business continuity that survives the worst day, evidence handling that stands up in court, and metrics that tell you if you are actually getting better.

Security Logging and Monitoring

Logging is the act of recording what happened. Monitoring is the act of watching those records for meaning. Most organizations log too much of the wrong things and too little of the right things. They drown in verbose firewall logs of allowed connections but miss the single failed login that preceded a successful breach. Effective logging starts with intent. Every log entry must answer the five Ws: who did what, when, where, and with what result. A log entry that says “User logged in” is useless. A log entry that says “User alice from IP 203.0.113.45 successfully authenticated via SSH to server web-prod-03 at 2024-11-08T03:14:22Z using public key authentication” is evidence.

The sources of truth are everywhere. Operating systems generate audit trails. Firewalls see every conversation. Web servers know every request. Databases know every query. Cloud providers log every API call. Endpoints see every process execution. Identity providers know every authentication. The challenge is not generating logs; it is collecting them before they rotate away, normalizing them into a common language, and storing them where they cannot be tampered with. A log that the attacker can delete is not a log; it is a wish.

Collection must be centralized. Syslog over TLS, agents like Filebeat or Elastic Agent, cloud-native forwarders, API pulls from cloud providers — the mechanism matters less than the guarantee of delivery. Agents are preferred over syslog for endpoints because they survive reboots, handle multiline events, and survive network blips. For network devices, syslog over TLS with structured parsing is standard. For cloud, native API ingestion is superior to log forwarding because it captures the full API context.

Once collected, logs must be normalized. A firewall calls it “source IP.” The endpoint calls it “source IP.” The cloud calls it “sourceIP.” The SIEM must map all of these to a single field — source.ip — so that a query for “all activity from 203.0.113.45” actually returns everything. The Elastic Common Schema (ECS) and the Splunk Common Information Model (CIM) are the two dominant standards. Adopting one eliminates the endless regex wrangling that wastes analyst time.

Retention is a legal and operational decision. Compliance frameworks dictate minimums — PCI DSS wants one year, HIPAA six years, CERT-In demands 180 days. But operational utility often demands more. Hot storage (SSD, searchable in seconds) for ninety days lets analysts hunt recent campaigns. Warm storage (compressed, searchable in minutes) for a year supports trend analysis. Cold storage (object storage, Glacier, tape) for seven years satisfies regulators. Immutable storage — S3 Object Lock in compliance mode, WORM tape, Azure Immutable Blob — is non-negotiable for the copies that matter. If an attacker with domain admin credentials can delete the logs, the logs are not evidence; they are a courtesy.

Monitoring is the active layer on top of logs. It has three modes. Real-time alerting watches for known bad: a signature match for Mimikatz, a brute-force threshold crossed, a known bad domain resolved. Threat hunting is proactive — analysts form a hypothesis (“APT29 uses WMI for lateral movement”) and query the data to prove or disprove it. Anomaly detection uses baselines — “this user never logs in at 3 AM from a new country” — to surface the unknown unknowns. Dashboards are for situational awareness, not decoration. A dashboard that nobody looks at during an incident is waste. Every dashboard must answer a question: “Are we under attack right now?” “Are our critical patches applied?” “Are our backups succeeding?”

SIEM Fundamentals and Event Analysis

A Security Information and Event Management system is not a magic box. It is a database optimized for time-series event data with a rules engine bolted on. Its value comes from three capabilities: ingestion at scale, a query language that lets analysts ask questions at the speed of thought, and a correlation engine that connects dots across sources.

Ingestion must handle bursts. A ransomware outbreak can multiply log volume by fifty times in minutes. The pipeline — whether Kafka, Kafka, Kafka, or a direct ingest API — must absorb the spike without dropping events. Parsing happens at ingest. Grok patterns, JSON extraction, JSON extraction, field mapping, type coercion — this happens once, at ingest, so queries remain fast. Enrichment happens here too: GeoIP for IPs, asset ownership from CMDB, user identity from Active Directory, threat intelligence tags from MISP or commercial feeds. Enrichment at write time means every event carries context; analysts do not need to join tables at query time.

The correlation engine is where detection lives. There are three flavors. Rule-based correlation is deterministic: “five failed logins for the same user from the same IP in five minutes.” It is fast, explainable, and brittle — attackers change one parameter and the rule misses. Statistical correlation looks for deviations from baselines: “this server usually sends 2 MB/hour to the internet; now it sends 2 GB.” It catches the unknown but generates noise. Behavioral correlation uses machine learning or graph analysis to spot patterns that match known adversary behavior — “this process tree looks like Cobalt Strike,” “this login sequence matches APT29’s TTPs.” The best SIEMs blend all three.

Event analysis is the analyst’s craft. When an alert fires, the analyst does not just read the alert. They pivot. They ask: what else did this user do? What else happened on this host? What did the process tree look like? What did the network traffic look like five minutes before and after? They pivot across data sources: the EDR saw the process execution, the firewall saw the outbound connection, the DNS logs show the domain resolution, the proxy saw the HTTP POST. The analyst builds a timeline. They ask: is this true positive? What is the scope? What is the blast radius? What is the next action? The SIEM must support this pivoting — fast, flexible, full-fidelity search across all data sources — or the analyst drowns.

Content is king. A SIEM without tuned rules is a noise generator. Rule tuning is continuous: suppress known benign patterns (the backup service that logs in every night at 2 AM), enrich with threat intelligence (this IP is a known C2), create composite rules (failed login + successful login + unusual process = compromise). Detection-as-code treats rules as code: version-controlled, tested against benign and malicious corpora, deployed via CI/CD, versioned, reviewed. This is detection engineering — the discipline of turning analyst intuition into code that runs at machine speed.

Incident Response Lifecycle

An incident is not an alert. An alert is a signal. An incident is a confirmed violation that requires coordinated action. The lifecycle, defined by NIST SP 800-61 Rev. 2, has four phases: Preparation, Detection and Analysis, Containment Eradication and Recovery, and Post-Incident Activity. Each phase has a purpose, and skipping one guarantees a worse outcome next time.

Preparation is the only phase that happens before the incident. It is the only phase where you have time. It means having an incident response plan that is not a PDF on a share but a living document with assigned roles, communication trees, escalation matrices, and pre-approved authorities. It means having a jump bag — forensic workstations, write-blockers, evidence bags, chain-of-custody forms, bootable forensic USBs, contact lists for legal, PR, law enforcement, cloud provider support. It means having a jump bag for the cloud: IAM roles pre-configured for forensic access, automated snapshot scripts, isolated forensic VPCs ready to receive snapshots. It means the team has practiced. Tabletop exercises quarterly. Red team exercises annually. Red team exercises where the blue team does not know it is an exercise. The muscle memory built in peace saves lives during war.

Detection and Analysis is the moment the alarm fires. Triage is the first act: is this real? What is the scope? What is the severity? The analyst must answer: what happened, when, where, who, how. They build the timeline. They preserve the volatile evidence first — memory, network connections, running processes — because it vanishes on reboot. They do not reboot. They do not run antivirus. They do not “clean up.” They preserve. They enrich: who owns the IP, what is the asset criticality, is there threat intel on the IOC, what does the user do, what is the asset’s value. They classify severity: Critical (active ransomware, data exfiltration, domain controller compromise), High (credential theft, malware on critical server), Medium (phishing click, policy violation), Low (port scan, policy violation). The severity drives the response speed and the notification chain.

Containment is the first action that stops the bleeding. Short-term containment is surgical: block the IP at the firewall, disable the compromised account, isolate the host in a quarantine VLAN, revoke the stolen token. It buys time. Long-term containment is architectural: rebuild the affected segment with patched systems, rotate all credentials in the trust zone, deploy additional monitoring, harden the configuration. The containment decision is a risk decision: destroying evidence vs. stopping spread. The rule: preserve evidence first if possible, but never let containment delay cause greater harm.

Eradication is the removal of the attacker’s presence. It is not “run antivirus.” It is: identify every persistence mechanism (scheduled tasks, WMI subscriptions, registry run keys, SSH keys, Golden Tickets, Skeleton Keys, Docker containers, Kubernetes pods, serverless functions). Remove them all. Patch the root cause (the unpatched CVE, the phished credential, the misconfigured S3 bucket). Rotate every credential the attacker touched or could have touched — because you do not know which ones they copied. Rebuild from known-good images, not “cleaned” systems. The attacker’s persistence is often deeper than the initial finding.

Recovery is the return to business. It is not “turn it back on.” It is phased restoration: core infrastructure (AD, DNS, PKI), then tier-1 applications, then tier-2. Restore from backups that were verified clean — verified by scanning, by hash comparison, by restoring to an isolated VLAN and running integrity checks. Monitor the restored systems with enhanced logging for thirty days. The attacker often returns to the same door.

Post-Incident Activity is where the organization learns. The incident report is not a blame document. It is a timeline, a root cause analysis (five whys), a list of what worked, what failed, what was lucky, what was missed. It produces action items with owners and due dates: “implement MFA on VPN by Friday,” “deploy EDR to the remaining 200 endpoints,” “update the playbook for ransomware.” The lessons feed back into Preparation. The cycle closes.

Vulnerability Management

Vulnerability management is not scanning. Scanning finds holes. Vulnerability management is the discipline of deciding which holes to fill, when, and verifying they stay filled. It is a continuous lifecycle: discover, assess, prioritize, remediate, verify, report.

Discovery requires visibility. Agent-based scanning (endpoint agents) sees installed software, missing patches, configuration drift. Network scanning sees exposed services. Cloud APIs see cloud resource misconfigurations. Container registries reveal vulnerable base images. Source code repositories reveal vulnerable dependencies (SCA). The asset inventory is the denominator — you cannot patch what you do not know exists. The CMDB must be live, fed by discovery scans, cloud APIs, AD, MDM.

Assessment translates findings into risk. CVSS is a severity score, not a risk score. A Critical (9.8) on a test server with no data is lower risk than a High (7.5) on the domain controller with a known exploit. Risk = Likelihood × Impact. Likelihood comes from exploit maturity (CISA KEV, exploit-db, weaponized in the wild), exposure (internet-facing, internal, air-gapped), and threat actor interest. Impact comes from asset criticality (crown jewel, regulated data, safety system), data sensitivity, and operational criticality.

Prioritization is where most programs fail. They patch by CVSS score, not by risk. A modern program uses risk-based prioritization: CISA Known Exploited Vulnerabilities (KEV) catalog is the absolute priority — if it is in KEV, it is being exploited now. SLA: 24–72 hours. Next: weaponized exploits on internet-facing critical assets — 72 hours. High-value internal assets with weaponized exploits — 7 days. Everything else by tier. The CISA KEV catalog is the single most actionable threat intelligence feed for prioritization.

Remediation has four flavors. Patching is gold standard but slow. Immutable infrastructure rebuild (bake patch into golden image, deploy new, terminate old) is faster and cleaner than in-place patching. Virtual patching (WAF rule, IPS signature, RASP agent) buys time when patching is impossible — but it is a band-aid, not a cure. Risk acceptance is a formal, documented decision: “we accept this risk because patching breaks the only MRI machine in the region; compensating controls are network segmentation and enhanced monitoring; review in 30 days.” Every accepted risk has an owner, an expiry, and a review date.

Verification closes the loop. Re-scan the asset. Run the regression test. Confirm the vulnerability is gone. Close the ticket with evidence. Metrics: Mean Time to Remediate (MTTR) by severity, backlog age, patch compliance rate, scan coverage. These are the metrics the board sees.

Business Continuity Fundamentals

Security protects confidentiality and integrity. Business continuity protects availability. When the ransomware hits, when the data center floods, when the pandemic locks down the city, business continuity answers: how do we keep serving customers?

It starts with the Business Impact Analysis (BIA). For every critical function — order processing, payroll, patient care, trading platform — you define the Maximum Tolerable Downtime (MTD). If the trading platform is down for more than four hours, the firm loses its license. That is the MTD. From MTD you derive the Recovery Time Objective (RTO) — the target time to restore the function — and the Recovery Point Objective (RPO) — how much data loss is tolerable. The trading platform: RTO 2 hours, RPO 5 minutes. The internal wiki: RTO 24 hours, RPO 24 hours. These numbers drive the architecture.

Recovery strategies are tiered. Tier 0 (mission-critical): active-active across availability zones, synchronous replication, automated failover, RTO near zero. Tier 1 (critical): hot standby, synchronous replication, RTO minutes. Tier 2 (important): warm standby, hourly replication, RTO hours. Tier 3 (standard): daily backups, restore from backup, RTO 24 hours. Tier 4 (non-critical): weekly backups, restore on request.

The Business Continuity Plan (BCP) is the playbook. It defines the Crisis Management Team (CMT): who declares a disaster, who speaks to media, who talks to regulators, who authorizes spend. It defines the Crisis Management Team (CMT) — not the IT team, the business leaders. It has communication plans: pre-written templates for employees, customers, regulators, media. It has alternate work sites, laptop caches, emergency procurement cards. It has the recovery procedures for each critical system, tested and dated.

Disaster Recovery (DR) is the IT subset of BCP. It is the technical execution of restoring systems. The DR site can be hot (active-active, zero data loss, zero downtime), warm (standby, hourly replication, hours to activate), or cold (empty rack, power, cooling, bring your own gear). Cloud has changed DR: pilot light (core infra running, scale on demand), warm standby (scaled-down, auto-scale on failover), multi-region active-active. Cloud DR is cheaper and faster but requires IaC, tested failover, and tested data integrity.

Testing is the only thing that validates the plan. Tabletop exercises quarterly: “ransomware hits at 2 AM, walk through the first four hours.” Full failover test annually: cut the primary, fail over to DR, run production for four hours, fail back. The test fails? Good. Fix the gap. An untested plan is a wish.

Digital Evidence Handling

Digital evidence is fragile. A reboot destroys RAM. A copy command changes timestamps. A well-meaning admin “fixes” the server and destroys the chain of custody. The first rule of digital forensics: do no harm. The second: document everything.

The order of volatility dictates collection order. CPU registers and cache (gone in nanoseconds). RAM (gone on power loss). Network state (connections, ARP cache, routing table). Running processes. Disk. Remote logs. Physical configuration. You capture in that order. RAM capture tools: WinPMEM, DumpIt, LiME, AVML. Disk imaging: hardware write blocker (Tableau, Wiebetech), then dd, ewfacquire, guymager. Output formats: E01 (EnCase), AFF4, raw. Hash before and after (SHA-256). Verify the hash.

Chain of custody is the paper trail that proves the evidence is what you say it is. Every transfer: who, what, when, where, why, hash. Sealed evidence bags, tamper-evident tape, locked evidence room, access log. Digital evidence: hash verified at every handoff. Write-blockers are non-negotiable. Never mount a suspect drive read-write. Never boot the suspect OS.

Forensic analysis works on the image, never the original. Tools: Autopsy, FTK, EnCase, Volatility (memory), Plaso (timeline), Hayabusa (Windows event logs), Hayabusa, Hayabusa. Timeline analysis (Plaso) reconstructs the “when.” File system analysis finds deleted files, alternate data streams, prefetch, shimcache, amcache, SRUM, USN journal. Memory analysis (Volatility 3) finds hidden processes, injected code, encryption keys, network sockets, unencrypted credentials. Network forensics (Zeek, Wireshark, Arkime) reconstructs the conversation: files transferred, commands typed, credentials stolen.

Evidence preservation for court: write-block, hash, seal, log, store in evidence safe. Chain of custody form signed at every handoff. Expert witness preparation: the analyst must explain the tool, the method, the validation, the findings, in plain language. The evidence speaks; the analyst translates.

Security Metrics and Performance Measurement

You cannot manage what you do not measure. But measuring the wrong things creates false confidence. “Number of alerts” is a vanity metric. “Number of blocked attacks” is a vanity metric. “Number of certified staff” is a vanity metric. Good metrics drive decisions.

The framework: Leading indicators predict. Lagging indicators report. Leading: percentage of critical vulnerabilities unpatched beyond SLA, phishing click rate, detection coverage of MITRE ATT&CK top 20, patch deployment velocity, percentage of assets with EDR. Lagging: number of incidents, MTTR, data breached, downtime hours, audit findings.

The core IR metrics are the vital signs. Mean Time to Detect (MTTD): average time from occurrence to alert. Target: under one hour for critical. Mean Time to Contain (MTTC): detection to isolation. Target: under one hour for critical. Mean Time to Respond (MTTR): detection to remediation. Target: under four hours for critical. Mean Time to Recover (MTTR): outage to restoration. Target: within RTO.

Detection metrics: Detection Coverage (percentage of MITRE ATT&CK techniques with at least one detection rule). Alert Fidelity: true positives / total alerts. Target: > 50% fidelity. Alert Fatigue Index: alerts per analyst per shift. Target: under 10.

Vulnerability metrics: Mean Time to Patch (MTTP) by severity. Critical: 72 hours. High: 7 days. Backlog age: oldest unpatched critical vulnerability age. Target: zero.

Governance metrics: Risk Register currency (percent reviewed in 90 days). Risk Register coverage: percentage of assets with risk scores. Policy exception age: how many exceptions older than 90 days. Third-party risk coverage: percentage of critical vendors assessed.

The dashboard is not for the analyst. It is for the CISO to show the Board. Five metrics. Trend lines. Red/Amber/Green. Narrative: “We reduced MTTD from 4 hours to 45 minutes by deploying the new EDR and tuning the Sigma rules. We reduced critical vulnerability backlog from 47 to 3 by automating the patch pipeline.”
