## Broken object-level authorisation as the defining API risk Context: the OWASP API Security Top 10 ranks broken object-level authorisation (BOLA) as the number one API risk: an API returns or modifies an object based on an id in the request without checking that the authenticated caller is allowed that object, so changing the id reaches another user's data. It is common in mobile backends because the app "knows" the user and developers wrongly trust that, even though an attacker can call the API directly with any id [C16-M07-R2]. Why it matters for this module: it is the clearest proof that the client cannot be trusted and that authorisation must be enforced server-side on every request - the core of backend hardening. Lessons: enforce per-object authorisation server-side; never trust an id or user value from the client; test for BOLA.



## (FICTIONAL TEACHING SCENARIO): The API that trusted the app Context: HimalayaNotes' (fictional) backend assumes the app enforces access, so it skips server-side checks. What happened: an API configuration review (apicheck.py) found no required authentication, non-expiring tokens, a cleartext endpoint, no per-request authorisation, and no rate limiting - 5 HIGH findings, FAIL. Because the app is an untrusted client, every one of these was exploitable by calling the API directly, regardless of the app. Response: the team hardened the backend - required and expiring tokens, enforced TLS, per-object authorisation on every request, rate limiting, generic errors, minimal data - and the review returned PASS. They adopted the OWASP API Security Top 10 as the standard going forward. Lessons: never trust the client; enforce authentication, authorisation, transport and rate limiting server-side; verify with an enforcing review.
