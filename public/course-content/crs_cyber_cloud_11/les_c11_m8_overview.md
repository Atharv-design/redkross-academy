## About this module

Cloud incidents move at API speed, and so must the response. This final module adapts the incident response life cycle to the cloud: preparation (access, logs and runbooks that exist before you need them), detection and analysis using the logs from Module 5, containment of identities and workloads, evidence preservation with snapshots and log exports, eradication and recovery from clean, isolated backups, and lessons learned. The lab performs a first-hour response to a compromised identity and instance in the local mock. The module closes with the secure reference architecture that the course capstone (Part C) asks you to build.

## Why it matters

In June 2014 Code Spaces, a code-hosting company, reported that an intruder had gained access to its AWS control panel, demanded money and, when the company tried to regain control, deleted data and backups; the company said it could no longer operate (case study). Response in the cloud depends on preparation - especially backups and break-glass access that an intruder in one account cannot reach.

## Where it is used

Cloud incident response teams and SOCs, IR retainers, crisis management, disaster recovery, regulatory notification (CERT-In six-hour reporting, Course 01), and architecture governance.

## Learning objectives

1. Prepare cloud accounts for response: access, logs, runbooks and tooling.
2. Analyse cloud incidents by correlating identity, control-plane, data and network logs.
3. Contain compromised identities (keys, sessions, roles) and workloads (isolation) without destroying evidence.
4. Preserve evidence: snapshots, log exports, tagging, hashing and chain of custody.
5. Recover from isolated backups and verify clean state.
6. Design a secure cloud reference architecture.
