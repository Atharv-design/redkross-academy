## ChaosDB, August 2021 - when the provider's layer fails ---------------------------------------------------------------------- Context: On 26 August 2021 Wiz published its research on a vulnerability in Azure Cosmos DB's Jupyter Notebook feature, which Microsoft had enabled by default for some accounts in February 2021. The flaw could expose customers' Cosmos DB primary keys. Microsoft disabled the feature within 48 hours of the report and notified more than 30% of Cosmos DB customers to rotate their keys [C11-M01-R3]. Responsibility analysis: - Provider: fix the managed feature, notify affected customers, publish guidance. - Customer: rotate primary keys; review access logs for the exposure period; prefer identity-based access (Microsoft Entra ID with RBAC) over account keys where the service supports it; restrict network access to the account. Lessons: - Provider-managed features can carry risk; disable features you do not use. - Long-lived shared keys concentrate risk; plan to rotate them on demand. - Logging and network restrictions reduce the impact of provider issues.



## (FICTIONAL TEACHING SCENARIO): "The provider is secure, so we are" ----------------------------------------------------------------------- This scenario is fictional. Tamarind's auditors accepted the provider's ISO/IEC 27001 certificate as evidence for "cloud security". A later review found production and backups in one account, two administrators without MFA and no organisation-wide trail. The audit scope was corrected: provider reports cover the provider's layers; Tamarind now evidences its own layers with posture scans, IAM reviews and log configuration checks (Modules 2, 5 and 6).
