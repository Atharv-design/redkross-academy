## The xz Utils backdoor, CVE-2024-3094, 2024 Context: on 29 March 2024 CISA published an alert about a reported supply chain compromise affecting XZ Utils, stating that malicious code was embedded in versions 5.6.0 and 5.6.1, and advising users to downgrade to an uncompromised version such as 5.4.6 Stable [C21-M07-R1]. The CVE record (CVSS 3.1 10.0) states that malicious code was discovered in the upstream tarballs of xz starting with 5.6.0, and that the liblzma build process extracted a prebuilt object file from a disguised test file in the source code, which then modified functions in the library [C21-M07-R5]. Why it matters here: the malicious behaviour lived in release artefacts and build logic, not in obvious source changes. Distributions that built from the tarballs inherited it. The compromise was discovered before it reached most stable distributions, largely by chance. Lessons: - Provenance must connect artefacts to reviewed source; "built from the release tarball" and "built from the tagged commit" are different claims. - Build steps that execute test data or generated files are part of the attack surface and deserve review. - SBOMs plus deployment inventory answered the urgent question - where do we run xz 5.6.0 or 5.6.1? - within hours for organisations that had them (Module 2 L05). - Maintainer health is a supply-chain risk: much critical software rests on very few people.



## (FICTIONAL TEACHING SCENARIO): The tag that moved Context: Kestrel Pay (fictional) signed every release in CI and verified signatures in a nightly job. Deployments referenced tags such as kestrel-api:2.4.0. What happened: a contractor's registry credential, used for testing, had push rights to the production repository. A test build was pushed as 2.4.0 by mistake. The nightly verification flagged the tag the next morning, but a node that rescheduled pods overnight had already pulled the unsigned image. Response: deployments moved to digests; an admission webhook now verifies signatures before any pod is admitted; production repositories have immutable tags and push rights only for the release pipeline's identity; the contractor credential was revoked. Lessons: verification that runs after deployment is monitoring, not prevention. Bind deployment to digests and verify at admission.
