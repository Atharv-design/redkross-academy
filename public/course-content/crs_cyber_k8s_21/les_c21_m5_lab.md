## Practical 1: Segment and enforce the Kestrel namespace

**Objective:** Apply default-deny segmentation and the Restricted level, with a reachability matrix and Pod Security evidence.

**Difficulty:** Advanced.

**Required tools:** kubectl; LAB_ASSETS/C21/k8s (netpol/, netpol_test.sh, psa/).

**Prerequisites:** Lessons L01-L03; Kestrel workload deployed.

**Environment setup:** kubectl apply -f netpol/batch-pod.yaml

**Explicit authorised scope:** the local lab cluster; probes run between lab pods only.

**Step-by-step instructions:**

1. sh netpol_test.sh (stage 1).
2. kubectl apply -f netpol/01-default-deny.yaml; wait a few seconds; run the test (stage 2).
3. Apply 02-allow-dns.yaml and 03-frontend-to-api.yaml; test (stage 3).
4. Write one more policy that lets batch reach api on 8080 only, test, then remove it.
5. kubectl apply -f psa/legacy-ns.yaml; run label dry runs for baseline and restricted on namespace legacy and record the warnings.
6. Label kestrel with enforce, warn and audit at restricted (version v1.34) and dry-run psa/privileged-pod.yaml.

**Expected observations (execution-tested):** the three stages in section 3; no warnings for baseline and four violated controls for old-web at restricted; the privileged pod denied with six violated controls.

**Troubleshooting:** stage 2 shows REACHABLE - your network plugin may not enforce NetworkPolicy (CS2); DNS failures in stage 3 - check the kube-dns label in your cluster ("kubectl -n kube-system get pods --show-labels").

**Cleanup:** kubectl delete ns legacy; keep the kestrel policies.

**Learning outcome:** you can segment a namespace and prove it.

## Practical 2: Audit policy and detections

**Objective:** Run the hardened cluster with auditing, generate labelled activity, and detect it; then extend the detector.

**Difficulty:** Advanced.

**Required tools:** Docker; kubectl; Python; hardened/ and k8s/ folders.

**Prerequisites:** P1; Lesson L05.

**Environment setup:** sh hardened/start_hardened.sh; build its kubeconfig (port 16444); from k8s/ run "sh apply_all.sh rk-k3s-hard".

**Explicit authorised scope:** your own hardened lab cluster; all activity is generated by you against lab objects.

**Step-by-step instructions:**

1. Read audit-policy.yaml and explain, rule by rule, what it logs.
2. sh m05_activity.sh and keep its output.
3. python audit_detect.py ../hardened/audit-logs/audit.log
4. Map each alert to an action A1-A7. Which action produced no alert and why is that correct?
5. Find the exec records in the raw log (two records, one auditID) and note the verb and response code.
6. Add a detection AD7 for "a NetworkPolicy deleted in a namespace labelled rk.lab/policy=enforced", generate a test event, and show it firing.

**Expected observations (execution-tested):** six alerts as in section 3; A1 silent; exec recorded with verb get and code 101. Your AD7 is not part of the tested reference set; the instructor guide gives a model answer.

**Troubleshooting:** an empty audit.log - the hardened folder was not mounted (check start_hardened.sh was run from hardened/); no exec alert - your kubectl may still use SPDY, which records a different verb; AD1 matches the subresource either way.

**Cleanup:** keep the hardened cluster for Modules 6-8.

**Learning outcome:** you can design audit logging and turn it into tested detections.
