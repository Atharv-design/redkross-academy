## PlayStation 3 ECDSA, 2010 - one constant nonce ---------------------------------------------------------------------- Context: At the 27th Chaos Communication Congress in Berlin in December 2010, the group fail0verflow presented their analysis of the PlayStation 3's security. Sony's ECDSA signatures on firmware used the same nonce value for every signature instead of a fresh secret random value. With two signatures sharing the nonce, the private signing key can be computed algebraically. Contemporaneous reporting described the group as having calculated Sony's private key, which would allow anyone to produce software the console would accept as signed [C15-M07-R2]. Lessons: - Signature schemes that need a per-signature random nonce (ECDSA, DSA) fail completely if the nonce is reused or predictable. - Prefer deterministic nonce generation (RFC 6979) or Ed25519, which removes the dependency on randomness at signing time. - Key compromise of a signing root has permanent consequences for devices in the field. Design for key rotation and revocation in firmware update systems. Verification note: from contemporaneous reporting (web-search cross-check); the original presentation slides were not reviewed.



## (FICTIONAL TEACHING SCENARIO): The restored counter -------------------------------------------------------------------------- This scenario is fictional. Tamarind's tracking service used AES-GCM with a counter nonce stored in a database row. After a failed upgrade, the database was restored from the previous night's backup, and the counter went back by 40,000. For the rest of the day the service reused nonces under the same key. A reviewer spotted duplicates using the monitoring query from the deep dive. The response was to rotate the key, re-encrypt the affected records, and switch to per-record data keys, so a counter restore could not cause reuse again.
