HTTP methods express intent. GET retrieves and should be SAFE (no state change) and idempotent; POST submits data and MAY change state; PUT and DELETE replace and remove; HEAD and OPTIONS are metadata [R1]. A core security rule follows: state-changing actions must not be done with GET, because GET requests are triggered by links, images and prefetch, which is exactly how CSRF works (Module 6). Status codes classify the result: 2xx success, 3xx redirection, 4xx client error (401 Unauthorised, 403 Forbidden, 404 Not Found), 5xx server error. Headers carry metadata and much of the security posture: Set-Cookie (with HttpOnly, Secure, SameSite), Content- Security-Policy, X-Content-Type-Options, Strict-Transport-Security. Reading headers is the fastest way to assess an application's hygiene - the lab's vulnerable app sets none of the security headers, which the mapping tool flags immediately.
