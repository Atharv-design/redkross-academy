## SSRF and cloud metadata Context: cloud platforms expose an instance metadata service at a fixed link- local address (169.254.169.254) that returns configuration and, in some setups, temporary credentials to code running on the instance. SSRF turns this into a serious risk: if a server can be made to fetch an attacker-chosen URL, the attacker can point it at the metadata endpoint and read data or credentials the server can access but they cannot. This pattern has featured in major cloud breaches, and it is a core reason SSRF defence must block internal and link-local addresses, not just external ones [C06-M06-R3]. Why it matters for this module: SSRF's danger is the server's PRIVILEGED network position. Defences must assume the attacker will aim inward - at metadata, internal services and loopback - and block those explicitly, with a default-deny allowlist and network segmentation. Cloud providers also offer hardened metadata modes that require a session token, which should be enabled. Lessons: block internal/link-local/loopback destinations; default-deny outbound; enable hardened metadata services; and segment the network so a bypass reaches little.



## (FICTIONAL TEACHING SCENARIO): The avatar fetcher Context: Sahyadri Reads (fictional) added a feature to set a profile avatar by URL, and the server fetched whatever URL the user supplied to cache the image - the same open-fetch pattern as the lab's /fetch. What happened: a user supplied an internal URL (an admin service and, in testing, the metadata address) instead of an image. The server dutifully fetched them and returned the contents, exposing internal information through the server's network position - classic SSRF. Response: the team stopped fetching raw user URLs; they required an uploaded image file instead, or restricted fetching to a default-deny allowlist of image CDNs; blocked private, loopback and link-local addresses with resolve- then-check; and segmented the fetching component. They also enabled the cloud's hardened metadata mode. Lessons: do not fetch arbitrary user-supplied URLs; prefer uploads or allowlisted destinations; block internal ranges; and remember the server can reach what the user cannot.
