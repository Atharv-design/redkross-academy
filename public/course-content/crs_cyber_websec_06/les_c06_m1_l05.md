A SESSION ties a series of requests to one authenticated user. The common pattern: the user logs in; the server creates a session and returns a session identifier in a cookie; the browser sends it on each request; the server looks it up to know who the user is. The security of the whole application rests on this identifier being unguessable, unforgeable and protected. Two failures recur: a PREDICTABLE token (the lab's vulnerable app uses base64(username) - trivially forgeable), and a token that is not protected by cookie attributes (so it can be stolen by XSS or leaked over HTTP). The fix is a random, server-side session identifier (for example Python's secrets.token_urlsafe) stored in an HttpOnly, Secure, SameSite cookie - which is exactly what the hardened app does. Identity is only as strong as the session mechanism that carries it (Module 3 goes deeper).
