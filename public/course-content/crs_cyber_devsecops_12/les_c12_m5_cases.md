## Log4Shell, December 2021 - the inventory problem ------------------------------------------------------------------------ Context: CVE-2021-44228 in Apache Log4j 2 allowed remote code execution through the library's JNDI lookup feature. Affected versions were 2.0-beta9 to 2.14.1. CISA's guidance recommended upgrading to 2.17.1 (Java 8), 2.12.4 (Java 7) or 2.3.2 (Java 6), and noted related CVEs addressed by later releases. CISA issued Emergency Directive 22-02 on 17 December 2021. Its guidance stressed finding every use of Log4j: scanning hosts and file systems, including internally developed and non-internet-facing software, and reviewing SaaS and cloud services [C12-M05-R1]. Lessons: - A ubiquitous transitive dependency becomes an organisation-wide emergency overnight. - SBOMs from builds, stored per release, turn "where are we affected?" into a query instead of a hunt. - Fixes arrived in several rounds (multiple related CVEs), so pipelines must make repeated upgrades fast and safe. - Vendors must be able to answer customers' SBOM and "are you affected?" questions quickly (SSDF RV).



## (FICTIONAL TEACHING SCENARIO): The clean manifest ------------------------------------------------------------------------ This scenario is fictional. Tamarind's supplier provided an SBOM listing five components, all with no known vulnerabilities. A scan of the actual container image found 140 packages, including an outdated transitive XML parser with a critical advisory. The SBOM had been generated from the top-level manifest. Tamarind now requires SBOMs generated from built artefacts and verifies them with its own scan.
