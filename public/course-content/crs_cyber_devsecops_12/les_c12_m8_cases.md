## xz Utils, 2024 - when release artefacts differ from reviewed source --------------------------------------------------------------------------- Context: On 29 March 2024, Andres Freund reported to the oss-security list that the xz 5.6.0 and 5.6.1 release tarballs contained injected code, leading to a backdoor affecting SSH servers on some Linux distributions. He noted that parts of the malicious material were committed to the upstream repository as test files, while the code activating them was present in the release tarballs [C12-M08-R1]. CISA issued an alert the same day (CVE-2024-3094), advising users to downgrade to an uncompromised version [C12-M08-R2]. The problem was found because of an unexplained performance change, as described in Course 09 Module 6. Lessons for release security: - Verify that release artefacts correspond to reviewed source, and prefer builds from version control over hand-made tarballs. - Opaque test fixtures (binary blobs) deserve scrutiny in review. - Maintainer and release processes are part of the supply chain, so signing and provenance should cover them. - Downstream consumers benefit from SBOMs and quick version queries ("which of our systems have xz 5.6.x?") to respond on the same day.



## (FICTIONAL TEACHING SCENARIO): The green report ---------------------------------------------------------------------- This scenario is fictional. A Tamarind release report showed all gates passing. A customer asked for the SBOM and found 40 packages, including a web framework the service does not use. Investigation showed the SBOM had been generated from the CI image, which contained the scanning tools. The team separated tool and product environments, as in this module's lab, regenerated the SBOM, and added a check that SBOM components match the lock file.
